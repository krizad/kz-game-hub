# Hand Duel (RPS) UI Implementation Plan

**Goal:** Make simultaneous throws, round reveals, and match scoring feel immediate and fair.

**Architecture:** Use existing activePlayers, choicesMade, roundWinner, gameWinner, and scores; conceal opponent choices until server resolution.

**Tech Stack:** Next.js client components, React, Tailwind CSS, Framer Motion, th/en dictionaries, existing Playwright E2E flows.

## Global constraints

- Keep server-authoritative state and the existing socket protocol; do not change game mechanics or scoring.
- Keep private roles, words, hands, and unrevealed choices out of public UI and room broadcasts.
- Keep Thai and English copy aligned; verify layouts at mobile width.
- Extend the existing game E2E flow for new or changed interactions and run the focused spec plus web typecheck.

## Tasks

- [ ] Make active duelists and queue/rotation order visible without crowding throw controls.
- [ ] Show a ready/locked state after a player chooses while keeping the opponent’s throw concealed.
- [ ] Reveal both throws together, then show round winner/draw, reason, and updated score.
- [ ] Keep best-of target and wins-to-match progress visible.
- [ ] Make throw controls touch-friendly and label rock, paper, scissors for keyboard/screen readers.
- [ ] Extend E2E for hidden choices, simultaneous reveal, draw, and match result; run rps.spec.ts and typecheck.

## Acceptance criteria

- Neither player sees the opponent’s choice before resolution.
- Locked players know they are waiting.
- Round winner and match score are clear.
- Reduced-motion mode preserves all state information.

## Engagement polish

- Use Framer Motion to lock each local throw, then reveal both choices together after the server resolves the round. Preserve the simultaneous reveal and never animate hidden opponent choices early.
- Use a restrained result transition for each round and the shared confetti helper only when the match ends with a winner.
